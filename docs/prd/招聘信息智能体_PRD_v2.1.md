# 多候选人求职招聘 Agent 产品需求文档



版本：v2.1（修订稿）  

状态：设计、开发、测试和验收基线  

更新时间：2026-09-03



## 1. 产品定义、目标与边界



本产品帮助候选人持续发现、筛选和接收适合的招聘岗位。系统从候选人资料、求职偏好与候选人画像出发，完成搜索计划、渠道采集、岗位标准化、候选人级评价、日报推荐、告警和招聘打招呼话术生成。



系统不自动投递、不自动向招聘方发送消息、不绕过登录、验证码或平台风控。招聘打招呼话术只生成供人工复制使用的草稿。



### 1.1 产品目标



- 将候选人资料转为可版本化的候选人画像和搜索计划。
- 以共享采集、候选人独立评价的方式支持多候选人，避免重复采集和数据串扰。
- 只推送可信、可追溯、未重复送达的岗位；渠道失败时不使用旧采集结果冒充当日数据。
- 登录失效、采集失败、发送模块不可用、AI 失败均可见、可恢复、可审计。
- 通过统一内部发送模块快速发送日报和告警；发送模块不可用时保留受控的智能体本地发送兜底。

### 1.2 范围与非目标



范围包括候选人资料与偏好、AI 画像与搜索计划、渠道登录和采集、岗位库、评分与推荐、日报/告警、打招呼话术、运行审计。



非目标包括自动投递、自动招聘沟通、验证码处理、规避平台风控、完整 SaaS 后台和未经确认的职业决策。



## 2. 角色、对象与隔离



| 角色/对象 | 职责与边界 |
|-|-|
| 候选人 | 管理本人资料、偏好、推荐反馈、画像和搜索计划修订；人工处理平台登录和招聘沟通。 |
| 维护者 | 管理渠道账户、运行状态、固定词、单次登录、草稿和故障处理；遵守最小必要访问。 |
| 渠道采集 Agent | 按平台和渠道账户登录检查、采集和标准化；只写共享岗位与渠道运行记录。 |
| 候选人子 Agent | 读取共享岗位和本人资料，产生本人评价、推荐、话术草稿；不得改写其他候选人数据。 |
| 岗位推荐话术 Agent | 将岗位编号、岗位链接、截图 OCR 或粘贴岗位描述规范化为岗位文字，并结合候选人画像生成打招呼草稿。 |



所有候选人级记录必须带 `candidate_id`、版本和来源 run_id。岗位是共享资产；评价、推荐、话术、通知偏好与人工状态是候选人私有资产。



## 3. 核心实体与数据原则



一期以 SQLite 为唯一业务事实源，启用 WAL 和单写入队列；JSON 保留原始渠道响应、AI 原始响应与 Run Manifest；CSV 仅作中文表头的人工导出；Markdown 用于 Profile、Query Plan 和日报审阅。



| 实体 | 最低关键字段 |
|-|-|
| Candidate / ProfileVersion | candidate_id、状态、资料来源哈希、profile_version、自动生效时间、修订记录、通知偏好。 |
| QueryPlan / QueryItem | candidate_id、plan_version、query_id、来源、渠道、优先级、启停、有效期、校验结果。 |
| ChannelAccount / ChannelRun | account_id、platform、browser_profile、登录状态、run_id、步骤状态、错误分类。 |
| Job / JobSnapshot | job_id、platform_job_id、display_id、公司、岗位、薪资、地点、JD、招聘方/发布人信息、活跃时间、canonical_url、内容哈希、采集证据。 |
| CandidateJobAssessment | candidate_id、job_id、snapshot_hash、profile_version、rule_version、规则/AI 结果、风险、评价时间。 |
| Recommendation / Delivery | candidate_id、job_id、推荐批次、业务周期、内容哈希、草稿、送达状态、发送通道、人工状态。 |
| NotificationAttempt | event_type、run_id、目的地、主发送尝试、兜底尝试、错误分类、幂等键、本地日志引用。 |



### 3.1 岗位编号与外部契约



`display_id` 是面向人工和消息场景的稳定岗位编号。BOSS 默认使用 A 前缀、猎聘默认使用 B 前缀；近似重复岗位可使用主编号后缀，如 `A032-b1`。编号一经分配不得因排序、导出或重新采集而变更。



招聘 Agent 是岗位编号和岗位档案的唯一事实源。其他应用必须通过版本化查询接口或进程内服务获取岗位，不得直接读取内部 JSON 文件。接口应返回岗位编号、岗位快照、状态、来源版本和访问范围；并明确 `not_found`、`ambiguous`、`closed`、`stale`、`forbidden` 等结果。群聊绑定须明确候选人上下文，避免跨候选人查询和泄露。



### 3.2 端到端业务流程



1. 候选人提交资料、偏好和脱敏授权；系统提取文本并生成自动生效的 Profile。
2. 系统生成并校验 Query Plan，合并候选人固定词和全局固定兜底词。
3. 在电脑开机的可执行窗口内，按渠道账户完成健康检查和共享采集；失败渠道单独阻断并告警。
4. 系统标准化、去重、保留采集证据并写入共享 Job 与候选人命中关系。
5. 每名候选人的子 Agent 对合格 fresh Job 完成硬过滤、规则评分、可选 AI 复核和推荐草稿。
6. 日报在本周期截止前发送并回写 Delivery；发送失败的合格岗位保持 pending_delivery，顺延下一周期。
7. 仅依据本周期 fresh 或当日重新验证结果刷新岗位生命周期，并生成可审计 Run Manifest。

## 4. 候选人资料、Profile 与搜索计划



候选人提交简历文件或等价文字、补充信息、结构化求职偏好和脱敏 AI 使用授权。偏好至少包括城市/区域、目标岗位、薪资、工作方式、行业、排除项、活跃度偏好、日报时间和通知目标。



系统可处理 PDF、DOCX、图片和纯文本，保存文件位置、哈希、提取状态和授权状态。手机号、邮箱、证件号、完整住址等不进入画像、搜索词、推荐提示词或普通日志。



Profile 生成后，如结构校验通过即自动成为 active 版本，不以人工确认作为前置条件；候选人可事后查看、修订并形成新版本。Profile 必须包含资料来源、求职目标、城市薪资、目标角色、排除项、最近三年优先经历、最近五年可用经历、可验证优势、能力边界、推荐/话术原则和待确认项。AI 不得虚构经历。



Profile 生效后自动生成候选人级 Query Plan。AI 词必须通过城市、排除项、平台限制、重复、数量和候选人偏好校验；人工固定词作为不可被 AI 删除的兜底层。运行时使用结构化计划，Markdown 用于审阅和审计。



AI 失败时使用最近有效计划；无有效计划则仅运行固定词并记录降级。某候选人全部专属词不可用时，仅暂停该候选人的专属查询和评价，不阻断共享渠道采集或其他候选人流程。



### 4.1 AI 调用配置、优先级与降级



所有需要模型能力的功能（画像、搜索计划、AI 推荐复核、岗位话术）必须通过统一的 `AIProviderRouter` 调用，而不是在各脚本中硬编码 API。每个任务类型配置可用 Provider 列表、模型参数、超时、重试上限、预算、结构校验器和降级策略。



默认优先级为：



1. `codex_runtime`：若当前运行环境可调用已登录、已配置的 Codex 智能体/模型能力，则优先使用该能力；此路径使用 Codex 当前可用的模型设定，不要求业务项目另配 OpenAI API Key。
2. `configured_api_provider`：Codex 运行能力不可用、该任务不支持或调用失败后，按配置顺序调用其他已配置 API Provider。
3. `task_fallback`：API 同样不可用时，按任务类型执行已声明的确定性兜底；没有兜底时返回 `ai_unavailable`，不得伪造 AI 产物。

`codex_runtime` 与 API Provider 是不同调用路径，必须分别健康检查、配置和记录。Router 至少记录 task_type、候选 Provider、实际 Provider、模型/版本、调用耗时、输入输出哈希、错误分类、重试和 fallback 链路；日志不保存未经脱敏的简历、JD、密钥或完整提示词。错误分类至少包括 `codex_unavailable`、`codex_timeout`、`api_unavailable`、`api_timeout`、`schema_invalid`、`budget_exceeded` 和 `ai_unavailable`。



各任务的最低兜底规则如下：已有 active Profile 时画像更新失败可继续使用上一版本；搜索计划失败使用最近有效计划或固定词；AI 推荐失败使用规则排序并标注降级；岗位话术仅在存在已配置规则话术兜底时使用该兜底，否则明确提示“AI 调用不可用，请稍后重试或手动编写”。所有无兜底失败必须写入 Run Manifest、AI 调用日志和本地运行日志；当故障状态变化或恢复时产生相应告警。



## 5. 采集、浏览器和登录运行模型



### 5.1 开机感知的采集窗口



本机运行不以固定时刻作为唯一触发条件。系统按上海时区评估窗口资格：上午 09:00–12:00 至少采集一次；下午 12:00–19:00 至少采集一次。每个渠道账户配置最小采集间隔，避免两次采集过近和平台风控风险。电脑整个窗口未开机时不补跑，只记录 missed_window；下一个可运行窗口正常开始。



健康检查可以按小时执行，但采集不默认按小时执行。各候选人的 Query Plan 在上午采集后生成或更新下午策略，在下午采集后更新下一周期策略。相同查询在共享采集批次中合并，并保留每个候选人的命中归因、优先级和 query_id。



默认日报目标时间为 19:00。若下午采集过早，且距离最近成功采集超过渠道配置的补采阈值，可在日报前尝试一次补采。若 19:00 时电脑未开机或流程尚未完成，报告可在当晚 21:00 前延迟发送；超过 21:00 未成功送达则不再补发当日，待发送岗位进入下一报告周期并标记为“上次未成功发送周期保留”。



日报成功送达时形成该候选人的业务截止点；截止点后的新增采集结果归入下一报告周期。当天发送成功后又采集的岗位也归入下一次报告。发送失败但已成功采集的岗位不得丢失，应保持为 pending_delivery 并顺延，不得伪造已送达。



### 5.2 单次人工登录与后台浏览器模式



每个 ChannelAccount 使用独立或显式共享的项目专用浏览器 profile。同一账户的浏览器操作必须串行。



| 模式 | 行为 |
|-|-|
| scheduled / normal | 自动启动或复用浏览器后，将窗口最小化到后台；执行登录检查和采集，不抢占用户前台。 |
| interactive_login | 维护者按平台和 account_id 单次触发；浏览器前台显示并打开对应登录页，供人工扫码、登录或完成安全验证。 |



触发 interactive_login 后，同账户自动化任务进入暂停或等待状态并获得互斥锁；其他独立账户可继续运行。用户完成登录后系统执行一次健康检查，成功则记录登录恢复、释放锁并恢复后台最小化模式。取消、超时、窗口关闭、安全验证未完成和健康检查失败均应记录明确状态，不得标记为 logged_in。系统不保存密码、不处理验证码、不绕过安全验证。重复登录请求应合并或拒绝，不能打开多个同账户登录窗口。



登录状态包括 `logged_in`、`login_required`、`security_check`、`cdp_unavailable`、`cdp_timeout`、`interactive_login_in_progress` 和 `unknown`。除 logged_in 外均不得采集。



### 5.3 新鲜度与岗位状态



每条采集、标准化、评分、推荐和草稿必须带 run_id、platform、business_cycle_id、created_at、source_run_id 和 freshness。fresh 的必要条件是本周期成功登录和采集、来源完整且校验通过。



渠道当天失败时，不得读取历史文件进入筛选、评价、推荐、推送、last_seen 或岗位关闭判断。历史岗位只有在当日重新验证仍开放时，才能以 `revalidated_carryover` 类型补充，并在日报中显著说明；未重新验证的历史岗位只可人工查看。



岗位关闭当前采用保守的连续缺失判断；后续增加低频、限速、可中断、按账户串行的详情页/接口强校验器，输出 `open`、`closed`、`security_check` 或 `unknown`。



## 6. 评价、推荐与招聘打招呼话术



评价分为硬过滤、规则评分和 AI 推荐复核。硬过滤覆盖城市、薪资、岗位类型、排除主题、采集可信度和活跃度。活跃度默认规则为：超过 7 天降级、超过 14 天低可行、超过 30 天排除；未知活跃度标为需确认，并按候选人规则决定是否进入推荐。



AI 仅复核规则 Top 候选，使用脱敏画像、岗位文字、规则评分和推荐历史。AI 失败时可生成明确标注“规则推荐，AI 未完成”的草稿，不得伪造 AI 理由。



推荐执行幂等和发送幂等必须分离。评价批次的幂等键至少包含 candidate_id、profile_version、rule_version、岗位输入快照哈希和触发批次；日报发送幂等键至少包含 candidate_id、business_cycle_id、report_type、目标会话和内容哈希。Query Plan 版本仅作发现来源，不应单独造成重复推荐。



### 6.1 招聘打招呼话术 Agent



话术 Agent 是可按需调用的候选人子 Agent。输入可为岗位编号、岗位链接、截图、OCR 文字或粘贴 JD；系统先将输入规范化为可追溯的岗位文字和结构化岗位事实，再结合当前候选人的 active Profile 生成 100–200 字中文打招呼话术。



输出必须包含岗位识别结果、话术草稿、所依据的候选人事实和待确认风险。不得虚构候选人的营销、海外、研发或其他经历；岗位无法识别、链接不可读或 OCR 置信度不足时要求补充信息。话术仅供用户人工复制发送，系统不得替用户向招聘方自动发送。



## 7. 日报、告警与发送策略



日报包含报告周期、渠道和数据状态、岗位编号、公司、岗位、薪资、地点、活跃时间、推荐理由、风险、更新原因、岗位链接和可选话术草稿。默认优先本周期 fresh 岗位；没有 fresh 数据的渠道只展示状态说明。



入站消息能力与主动推送能力分离。招聘 Agent 可在无需入站消息时快速触发日报、登录告警、采集告警和恢复通知。通知服务需区分岗位日报、系统告警、发送模块故障和恢复通知，并按事件类型使用独立幂等键和冷却窗口。



发送优先调用智能体内部配置的发送模块；该模块实际指向当前消息发送应用。请求至少包含 event_type、candidate_id、run_id、业务周期、目标 binding、内容、内容哈希和幂等键。发送应用负责常规渠道适配、限频和状态返回。



当发送模块健康检查失败或接口明确返回不可用、且可确认未被接收时，招聘 Agent 允许使用自身本地发送适配器进行受控兜底。若主模块返回 delivery_uncertain，则不得直接兜底重发，以免重复发送，应记录并等待人工或状态查询。每一次主发送、状态查询、兜底发送、失败和恢复均写入本地日志与 NotificationAttempt；首次模块不可用和恢复须生成可读告警。兜底发送同样必须带幂等键和最终送达状态。



## 8. 可观测性、安全与验收



每个 run_id 生成不可覆盖的 Run Manifest，记录候选人/渠道上下文、计划和画像版本、登录状态、采集、写库、评分、推荐、发送、兜底、岗位刷新、overall_status、错误和时间。关键指标包括渠道可用率、fresh 覆盖率、推荐重复率、发送成功率、发送模块兜底次数、登录恢复时长、人工介入率和候选人反馈。



AI 输入默认脱敏；候选人资料、推荐和人工状态按 candidate_id 隔离。原始文件、Cookie、密钥和账号信息不得写入报告、普通日志或飞书消息。候选人撤回授权后的停止、导出、保留期限、删除范围和备份清理须按数据保留策略执行。



### 8.1 关键验收



1. 两名候选人具有不同偏好时，岗位可共享采集，评价、推荐、话术和历史严格隔离。
2. BOSS 登录失效、猎聘成功时，BOSS 不产生筛选、推荐或旧数据推送；整体状态为 partial_success。
3. 维护者单次触发 BOSS 登录时，浏览器前台显示、同账户采集暂停；登录健康检查成功后浏览器最小化并恢复后续采集。
4. 上午/下午仅在电脑开机期间各至少执行一次，且不因错过窗口补跑；采集之间遵守最小间隔。
5. 19:00 未完成时报告可延至 21:00；21:00 后未送达的合格岗位顺延下一周期并保持未送达状态。
6. 发送模块不可用且确认未接收时，智能体本地兜底发送并记录日志；投递不确定时不自动双发。
7. 岗位编号、链接、截图和 OCR 输入均可进入话术 Agent；输出为 100–200 字且不虚构经历。
8. 同一岗位内容、规则和候选人状态未变化时不得重复送达；岗位变化或候选人规则跨阈值时重评并说明原因。

## 9. 上线顺序



先以草稿模式修复新鲜度、登录状态、业务周期和发送记录；再迁移 SQLite、候选人隔离与推荐/送达关系；随后接入主动推送与发送兜底；最后启用多候选人、话术 Agent 和岗位状态强校验。每次发布保留数据库备份、Run Manifest、回滚方案和关键验收记录。



## 10. 保留并扩展的原有详细需求



本章保留 v2.0 的完整产品模块，除非本修订稿有明确更改（例如自动激活、开机感知调度和发送兜底），其余约束继续有效。



### 10.1 成功标准与异常矩阵



| 指标 | 标准 |
|-|-|
| 候选人隔离 | 100% 候选人级事实带 candidate_id 与版本，不互相覆盖或查询泄露。 |
| 新鲜度 | 外发岗位必须为 fresh 或当日重新验证的 carryover；失败渠道不使用旧数据冒充本周期结果。 |
| 推荐去重 | 已送达且岗位内容、候选人规则和人工状态未变化的岗位不得再次送达。 |
| 渠道可见性 | 首次失败、故障类型变化、持续失败、恢复、发送模块不可用及其恢复均可见且有日志。 |
| AI 可控性 | 每项 AI 产物可追溯 Provider、模型、输入输出哈希、校验与降级链路。 |



文件解析或 OCR 置信度不足时不得以空画像搜索；画像与表单矛盾时以明确表单硬条件为准并记录待核对项；候选人撤回授权后停止新 AI 调用和推荐，并按保留策略处置资料。AI 词违反渠道或候选人硬规则时应拒绝并记录，不得静默改写。



### 10.2 多候选人编排与任务类型



共享采集不因候选人人数线性重复。系统合并相同平台查询，保留 CandidateQueryHit；候选人专属词按账号配额、公平性和最小间隔排入共享采集批次。不得存在全局 `current_candidate`。



| 任务 | 输入 | 输出 | 并发规则 |
|-|-|-|-|
| 资料解析/画像 | candidate_id、文件、表单 | Profile draft/version | 不同候选人可并发。 |
| 搜索计划 | active Profile、固定词、渠道能力 | Query Plan | 不同候选人可并发。 |
| 渠道采集 | platform、account、共享查询批次 | Job、ChannelRun、命中关系 | 同账户串行，不同独立账户受限并发。 |
| 评价与推荐 | Job 快照、Profile、规则、历史 | Assessment、Recommendation draft | 不同候选人可并发。 |
| 报告发送与回写 | 草稿、通知配置 | Delivery、Recommendation 状态 | 按候选人/目标会话/业务周期幂等串行。 |



### 10.3 推荐、AI 成本与人工操作细则



推荐必须记录推荐原因、风险、人工反馈、首次/最近推荐、内容哈希、草稿和真实 Delivery。候选人标记不感兴趣、已投递、已沟通、面试、拒绝或收藏后，下一轮排序必须遵守该状态。



AI 调用应具备输入长度限制、超时、重试上限、候选人或日预算、缓存和结构校验。相同 Profile/岗位/规则输入优先读 ai_runs 缓存。预算耗尽时停止低优先级 AI 调用并保留已声明的规则降级；不得静默失败。



候选人可修订资料、画像、固定词、搜索计划和推荐反馈；维护者可触发单次登录、查看渠道状态、预览草稿、重试被阻断渠道和发送测试消息。所有人工动作记录操作者、时间、原因、前后版本，且不得覆写原始采集证据。



### 10.4 当前实现差距、迁移与放行



现有 JSON/CSV 产物、全局候选人配置、全局推送状态和按“最新文件”回退均不得继续充当业务真相源。P0 为新鲜度门禁、渠道级 partial_success/blocked_login、登录/发送告警、Delivery 关联和密钥治理；P1 为 SQLite、候选人隔离、Query Plan、规则接通、AI Router 与共享岗位关联；P2 为详情状态强校验、多 Agent 运营指标和多账户扩展。



迁移顺序为：冻结真实自动推送并保留草稿；迁移历史 JSON/CSV 为只读来源；建立 SQLite 与备份；先以单候选人连续运行并通过新鲜度、登录、日报、发送兜底和话术验收；再启用第二候选人和并发；最后恢复真实日报。任何发布必须保留回滚脚本、数据库备份和 Run Manifest。



### 10.5 原有参考与审计边界



公开招聘提醒、来源健康和 Provider 抽象方案仅作研究参考，不引入其自动投递或自动沟通能力。现有实现审计、某日渠道故障、敏感配置扫描结果作为独立整改记录维护，不改变本 PRD 对未来产品行为的定义；审计发现的有效凭据必须立即轮换。



保留的公开参考包括 Job-alert-bot（来源健康、故障/恢复和稳定 ID 去重）、Job_Scraper（来源隔离与配置筛选）和 career-ops-cn（国内多渠道 Provider 抽象）。引用仅用于设计参考，不直接复用其自动沟通能力。
