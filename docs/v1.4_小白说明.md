# v1.4 客户端：小白版说明

这篇用尽量简单的说法，说明 v1.4 现在有哪些模块、怎么运转、为什么这样设计。

## 一句话

它是一个装在 Windows 上的“本地求职助手”：

- 打开后常驻在电脑上；
- 用本地 Chrome 登录 BOSS/猎聘；
- 按时间、间隔和空闲情况去采集岗位；
- 岗位先入库，再按“角色”分别评分；
- 在页面里看岗位、看评分、导出 Excel、看日报；
- 通过飞书发通知/日报。

所有数据都在本机，不上传云端；不自动投递，不自动和招聘方聊天，不绕过验证码。

---

## 1. 现在有哪些功能模块

### 1.1 启动器

文件：`启动招聘智能体.cmd`

双击后：

1. 检查 Electron 依赖；
2. 检查演示数据库；
3. 启动桌面窗口；
4. 如果桌面窗口起不来，自动打开浏览器版页面。

为什么：不用记命令、不用手动开 Node、不用找端口。

### 1.2 首页

- BOSS、猎聘两个独立渠道卡；
- 显示登录状态、上次检查时间；
- 可以“检查登录”“打开登录页”；
- 可以“立即执行一次调度”“手动生成采集任务”；
- 显示岗位数、角色数、最近任务。

“立即执行一次调度” = 按当前时间/空闲策略判断现在该干什么。  
“手动生成采集任务” = 不等到定时，直接给运行中角色排一次采集。

### 1.3 角色

一个“角色”就是一套求职方向，例如：

- 实施顾问；
- 交付专员；
- AI 项目经理。

角色最多 3 个。

角色创建时可以导入 Markdown 简历；系统保存原文、解析目标岗位/技能/经历，并关联 `resume_id`。

角色创建时不选渠道；点“确认渠道”时才勾选 BOSS/猎聘。  
没勾的渠道就不会为这个角色生成采集任务。

角色状态：

```text
待确认 → 待启动 → 运行中/已暂停
```

首次启动后锁定，不能改画像；想改只能复制一个新角色。

### 1.4 任务

任务分三层：

```text
一次采集事件
  └─ 平台 × 角色 的子任务（例如 BOSS-实施顾问、猎聘-实施顾问）
       └─ 关键词任务
```

每个子任务独立成功/失败；失败可以在采集窗口内重试。

任务可以暂停、继续、重试、强制关闭；卡住 5 分钟只通知，不自动重启 Chrome。

### 1.5 职位库

- 公共岗位库：岗位是什么、链接、公司、薪资、采集时间、是否重复/关闭；
- 角色评分库：这个角色对这个岗位打多少分、理由、风险、备注、是否打招呼；
- 同一岗位可以对不同角色有不同分数；
- 支持按角色导出 Excel 兼容文件，链接可点。

### 1.6 设置

- 采集日、采集时间段；
- 最低采集次数、最小间隔（最低 1 小时）；
- 日报时间；
- 空闲分钟、CPU、电量；
- 录入时是否再采集；
- 飞书 webhook。

### 1.7 AI 能力

- 配置 OpenAI 兼容 API 或 Codex 本地命令；
- 排序、测试、启用/关闭、删除；
- 前一个失败自动试下一个；全部失败走规则兜底；
- Key 本地加密，不返回明文。

### 1.8 日报/消息

- 按角色生成日报；
- 通过飞书群机器人发送；
- 日报日志保留 2 周；
- 通知（登录失效、风控、卡住、失败）也会记录。

原始项目里的“消息平台”是一个**独立服务**，负责飞书入站消息、群聊 Agent 会话、命令路由；v1.4 客户端目前只做了“日报/通知发送”这一层，没有把完整消息平台塞进客户端。两者边界见后文。

## 2. 核心逻辑

### 2.1 采集 → 入库 → 评分 → 日报

```text
采集
  → 写原始 JSON 文件
  → 登记入库队列（pending）
  → 入库 worker 处理所有未入库文件
  → 岗位库（客观事实）
  → 按角色评分
  → 日报/飞书
```

为什么把“入库”和“评分”分开？

- 入库只关心数据完整、去重、编号；
- 评分规则以后可以改、可以重算；
- 同一岗位可以对不同角色重新评分，不用重新采集。

### 2.2 采集时间 ≠ 入库时间

岗位记录：

- `collected_at`：什么时候采集到的；
- `first_seen_at`：第一次采集时间；
- `ingested_at`：什么时候写进数据库。

例如 11 号采集、12 号才入库，页面仍显示 11 号。这样不会把老岗位误判成新岗位。

### 2.3 编号和重复

- 岗位编号在真正写库时分配；
- 编号全局唯一、不回收；
- 同渠道精确重复：更新，不新增编号；
- 跨渠道同一岗位：仍入库、仍占号，但标记“重复于更早编号”；
- 角色评分库会同步“是否重复/是否关闭”。

### 2.4 多角色评分

公共岗位库只存客观信息；  
每个角色一个评分库，记：

- 岗位 UUID、岗位编号；
- 评分、评分时间、理由、风险；
- 备注、是否打招呼；
- 岗位状态/重复快照；
- 是否需要重新评分。

评分顺序：

1. 先排除重复/关闭；
2. 没有评分、评分早于角色修改时间、入库晚于角色修改时间 → 需要评分；
3. 新岗位优先；
4. 单次最多 100 个，有时间再处理旧岗位；
5. 岗位关闭后重新开放 → 重新进入评分。

### 2.5 调度

```text
09:00 采集窗口开始
12:30 如果今天 0 次，强制一次
窗口结束前 不够最低次数，补采
19:00 R-2h：0 次或勾选时兜底采集
20:00 R-1h：停止采集，入库/评分/生成日报
21:00 发送日报
```

强制采集只绕过“空闲判断”，**不绕过 1 小时间隔**。  
R-1h 不等采集，保证日报时间。

### 2.6 任务状态

```text
排队 → 运行 → 成功/失败
          ├→ 暂停 → 继续
          ├→ 重试
          └→ 关闭
```

任务有进度、心跳、checkpoint；程序重启后可以继续。

## 3. 架构

```text
启动器 .cmd
  └─ Electron 窗口 / 托盘
       └─ 本地 Node 服务（127.0.0.1:4780）
            ├─ SQLite 数据库
            ├─ 任务队列/调度
            ├─ 采集 worker（调用旧采集脚本 + Chrome CDP）
            ├─ 入库/评分/日报
            └─ 本地 HTTP API + 页面
```

为什么用“本地服务 + 页面”：

- 页面和后台逻辑分开，刷新页面不会丢任务；
- Electron 只负责窗口/托盘，后台用系统 Node 跑；
- 以后换界面、加 API 都容易；
- 数据都在本机 SQLite，不依赖云。

为什么不用 Electron 自带 Chromium 采集：

- BOSS/猎聘的风控认真实 Chrome；
- 外置 Chrome 用独立 Profile/CDP，最小化运行，人工可唤醒；
- 不把 Chrome 嵌进 Electron 窗口，避免焦点/输入法/反爬问题。

---

## 4. 为什么这样设计

- **入库和评分拆开**：采集一次，评分可以反复算；
- **岗位共享、评分按角色**：同一岗位不用重复采集，不同角色看不同结论；
- **编号写库时分配**：避免重复编号、空洞；
- **原始文件 + 队列**：晚上没跑、第二天也能补录；
- **任务状态机**：卡住/风控/暂停/恢复可见，不再“跑了 1 小时不知道在干嘛”；
- **角色首次启动锁定**：启动后写数据，画像再变会让历史评分失去意义；
- **渠道在确认时选**：创建角色只是画像，确认运行才决定去哪个平台找；
- **AI 只做辅助**：没有 AI 也能用规则跑，有 AI 再增强。

## 5. 目前还没完成/要注意

- 真实 BOSS/猎聘/飞书/AI 线上回归还没做；
- 角色级关键词还没有真正传入旧采集器；
- 简历目前是本地 Markdown 解析，不是 AI 深读；
- 原“消息平台”的入站群聊 Agent 还没有并入客户端，只保留了日报/通知发送；
- Electron 用 `--no-sandbox` 兼容当前 Windows 环境；
- 安装包还没生成；
- 旧 `daily_workflow` 仍走 v1.3 JSON，新链路走 `v14:*`/客户端。
