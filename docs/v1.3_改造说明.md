## 一、用大白话讲，改了什么

以前的流程像这样：

> 去招聘网站逛一圈 → 一边逛一边判断“这个岗位好不好” → 觉得不错才登记到本子（岗位库） → 再打分。

问题是：
- 还没登记就先筛掉，标准一改，之前筛掉的岗位就找不回来了；
- 登记的是“打分后的结果”，不是岗位本身，规则一改旧分数不会变；
- 一个关键词只翻第一页，前面的词把名额吃满，后面的词永远轮不到；
- 每天不知道“哪个词看了多少、重复多少、失败多少”。

v1.3 改成：

> 去招聘网站逛 → **先把岗位事实完整登记到本子（入库）并给编号** → 再根据本子上的事实打分 → 最后只把值得看的写进日报。

一句话：**先把事实存下来，再做判断；判断可以重算。**

## 三、数据怎么存

### 岗位库 `data/job_store.json`

每个岗位现在分三块：

```json
{
  "job_store_key": "boss:xxx",
  "display_id": "A012",
  "record_status": "active | duplicate",
  "facts": {
    "platform": "BOSS",
    "platform_job_id": "xxx",
    "job_url": "...",
    "company": "...",
    "job_title": "...",
    "salary_text": "20-30K",
    "city": "上海",
    "district": "徐汇区",
    "job_description": "完整 JD",
    "detail_status": "ok",
    "source_keyword": "AI项目经理",
    "source_page": 1,
    "content_hash": "..."
  },
  "score": {
    "rule_version": "...",
    "candidate_version": "...",
    "hard": { "status": "pass | need_confirm | fail", "failures": [], "need_confirm": [] },
    "soft": { "role": 88, "experience": 76, "ai": 86, "salary": 85, "..." : 0 },
    "overall": 81,
    "success": 72,
    "focus_level": "重点关注",
    "recommendation": "优先投递或优先沟通",
    "reasons": ["..."],
    "risks": ["..."],
    "ai": { "used": false, "delta": 0 }
  }
}
```

- `facts`：平台上客观存在的岗位事实；重采只更新这里。
- `score`：独立、可重算的评分；规则/简历变了可以只重算，不重新采集。
- `display_id`：入库时分配；按渠道 A/B 各自递增，写入成功即占用，不回收。
- `record_status=duplicate`：跨渠道同一岗位的晚入库记录；保留编号，但日报不推荐。
- 状态刷新使用采集器输出的 `seen_job_ids`（本轮列表实际看到的岗位），不再拿“新增入库文件”判断；`JOB_CLOSE_AFTER_MISSING_DAYS=0`（默认）只标“未知”，不自动关闭。

### 编号 `data/job_numbering.json`

按渠道保存计数器（A= BOSS，B=猎聘）。写入岗位库成功后才保存计数器；下次分配会同时扫描库内已有编号取最大值，避免“写了库但计数器没落盘”造成重号。

### 关键词档案 `data/keyword_profiles.json`

由每日账本重建（幂等，重复运行不会重复累加）。每个词、每个渠道记录：
使用次数、最近使用日期、最近一次看到/新增/重复/失败、最近 10 次历史。

### 采集账本 `data/collection_ledger/YYYY-MM-DD.jsonl`

一行代表一次“采集”或“入库”事件；汇总时按“渠道 + 关键词”合并成一行。人可读汇总在 `outputs/collection_ledger_YYYY-MM-DD.md`。

## 四、采集怎么翻页（BOSS）

1. 关键词计划给出 `target_new`（目标新增）和 `max_pages`（最大页数）。
2. 打开一页列表接口，先统计本页岗位。
3. 对每个岗位：
   - 有平台唯一 ID 且库里没有 → 打开详情；
   - 详情拿到完整 JD → 记录；
   - 没有 ID/详情 → 进待补。
4. 达到关键词目标、总预算、页数上限、重复率过高、页面重复 → 停止。
5. 详情不再“每打开一个岗位就重新搜一次关键词”，而是直接 `https://www.zhipin.com/job_detail/<encryptJobId>.html`。

猎聘同理，但页码参数在不同版本可能叫 `page` 或 `currentPage`；默认用 `LIEPIN_PAGE_PARAM=page`。如果第 2 页内容和第 1 页一样，会自动停止并记录 `page_repeat`，说明这个参数名需要按实际页面调整。

## 五、评分怎么算（重点）

### 1）候选人事实卡

`config/candidate_facts.json` 是“补充覆盖层”，留空时会从 `config/profile_rules.json` 和当前候选人画像派生：

- 目标城市、目标薪资、目标角色、优势关键词
- 避雷标题词、避雷 JD 词
- 是否允许纯技术岗
- 画像摘要（给 AI 用）

当前项目里的 `profile_rules.json`（AI 项目经理/20-25K/上海）会直接生效；测试夹具换成软件开发方向时，评分会自动切换成“工程岗权重”。

### 2）硬条件（先过滤，AI 不能改）

- 城市是否可接受；地点缺失 → “需确认”
- 薪资是否低于底线；薪资缺失 → “需确认”，不直接淘汰
- 标题是否销售/实习/管培/避雷词
- 纯技术岗且没有管理/交付/产品成分（候选人目标不是研发时）
- JD 命中避雷词 → 默认“需确认”（可在配置里改成直接失败）

硬条件不通过 → `暂不考虑`；需要补信息 → `需确认`；通过才进入软评分。

### 3）软评分

10 个维度，权重在 `config/scoring_rules.json`：

| 维度 | 说明 |
| --- | --- |
| role | 标题/职责与目标角色匹配 |
| experience | 简历优势词、技能与 JD 重合 |
| ai | AI/智能体/大模型相关 |
| delivery | 交付/实施/客户/需求推进 |
| product | 产品/方案/原型/需求设计 |
| domain | 行业/领域交集 |
| salary | 与目标薪资区间重叠 |
| location | 城市/区域/通勤 |
| activity | 招聘方活跃度 |
| confidence | 详情完整度 |

- 工程岗（目标角色含开发/研发/工程师）使用 `weight_profiles.engineering`：role/experience 权重更高，product/domain 权重更低。
- 项目/产品岗使用 `weight_profiles.project_product`。
- 输出总分、成功概率、分项分、3–6 条理由、1–6 条风险、建议动作。
- 关注等级：`重点关注` / `可关注` / `低优先` / `需确认` / `暂不考虑`。

### 4）AI 的角色（重点看这里）

AI **不是**决策者，只是“复核助手”：

- 默认 `AI_DEFAULT_MODE=disabled`，完全不调用；`AI_SCORE_REVIEW_ENABLED` 也默认 `false`，即使开启 AI 也要显式打开评分复核。
- 只有规则分 >= `AI_SCORE_REVIEW_MIN_SCORE`（默认 50）且硬条件 `pass` 的岗位才会送给 AI。
- 只取规则分最高的 `AI_SCORE_REVIEW_MAX_ROWS` 条（默认 8），不是全部。
- AI 返回 `delta`（整数，默认限制 -8..+8）、理由、风险；程序会再次 clamp，重新计算关注等级。
- **硬条件 `fail` / `need_confirm` 的岗位不会被 AI 提升**；`applyReview` 里还有二次保护。
- 结果按“岗位 key + 规则版本 + 候选人版本 + 模型”缓存到 `data/ai_score_cache.json`；同一岗位同一版本不重复调用。
- AI 失败/超时/关闭 → 保留规则评分，不影响日报。
- 评分变化不会触发重复推送；只有岗位事实（薪资/标题/地点/JD 等）变化才会重新推荐。

## 六、怎么运行

### 1）日常（定时/草稿）

`run_daily_job_agent.ps1` → `preflight` → `scheduled_entry` → `daily_workflow`，内部顺序已经是：

```text
collect → ingest → score → push → refresh
```

对应的环境变量：

- `ENABLE_COLLECT` / `ENABLE_INGEST` / `ENABLE_SCORE` / `ENABLE_PUSH`
- 旧的 `ENABLE_SCREEN` / `ENABLE_EVALUATE` 仍兼容（作为回退）
- `COLLECT_TARGET_NEW`、`BOSS_TARGET_NEW`、`LIEPIN_TARGET_NEW`：每轮每渠道新增入库目标
- `BOSS_MAX_PAGES` / `LIEPIN_MAX_PAGES`：每关键词最大页数
- `BOSS_DETAIL_ATTEMPT_LIMIT` / `LIEPIN_DETAIL_ATTEMPT_LIMIT`：详情尝试上限
- `INGEST_MIN_JD_CHARS`：入库最低 JD 字数

### 2）只重算评分（不重新采集）

```powershell
cd 招聘智能体\recruitment-agent
node .\src\evaluate\score_jobs.js --from-store --date=2026-10-28
```

或 `npm run rescore`。适合改了 `scoring_rules.json` / `candidate_facts.json` / 简历后使用。

### 3）手工分步

```powershell
node .\src\ingest\job_ingest.js .\outputs\boss_daily_20261028_jobs_xxx.json --date=2026-10-28
node .\src\evaluate\score_jobs.js .\outputs\boss_stage2_ingested_xxx.json --date=2026-10-28
node .\src\push\job_push_draft_and_send.js .\outputs\boss_stage3_scored_xxx.json
```

### 4）离线测试

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\自动化测试\run_offline_smoke.ps1
```

会跑：空包 preflight、消息平台回归、入库/编号/跨渠道重复、评分硬条件、AI 边界、关键词排序、账本汇总。默认不联网、不调用 AI、不发送飞书。

## 七、对“待确认项”的默认选择

需求文档里还有几个待确认项，这次先按以下默认实现，后续可改配置/小改代码：

| 待确认 | 本次默认 |
| --- | --- |
| 无平台 ID 时的唯一键 | **不入库**（需求明确“唯一 ID”是硬前提）；无 ID 进待补 |
| 跨渠道相似判定 | 公司/标题归一化后一致，且 JD 相似度 >=0.8，或地点+薪资完全一致 |
| 跨渠道重复是否占 30–50 额度 | 占编号，但单独计入 `new_duplicate`，不算 `new_primary`；总目标按新增主记录控制 |
| 主记录关闭后是否提升重复记录 | 暂不自动提升；后续可加“主记录 closed 时找重复记录” |
| 详情尝试上限 | 默认新增目标的 2 倍（至少 +5），可配 |
| 每关键词最大页数 | 默认 3，可配 |
| AI 微调幅度 | ±8 分，可配；只对规则高分且硬条件通过的岗位 |
| 关键词生成数量 | planner 每轮最多取 12 个，按优先级和久未使用排序 |
| 猎聘翻页参数 | 默认 `page`；如果实际是 `currentPage`，改 `LIEPIN_PAGE_PARAM` |
