## 0. 执行原则

1. 每个阶段独立可验证；完成即暂停，汇报状态并询问：
   - 继续下一阶段；
   - 还是先更新版本/推送代码/开 PR。
2. 不直接推 `main`；所有代码在 `feature/v1.4-client-20261105-210244` 分支提交，推分支后给 Compare/PR 链接，等用户合并。
3. 每个阶段必须：
   - 有自动化测试或可重复验证；
   - 有测试记录；
   - 对照需求检查偏离；
   - 不删除旧功能测试来“让测试过”。
4. 小步提交；阶段结束打一个阶段提交，不等全部做完再提交。
5. 本机 Windows；路径含中文，PowerShell 命令加引号。
6. 不提交 `.env`、API Key、简历原文、Chrome Profile、日志中的隐私字段。

## 2. S1：数据层 + 入库队列 + 采集时间

### 目标

- 建立 SQLite 数据层和迁移；
- 采集写 raw 后登记队列；
- 入库处理所有未入库 raw；
- 采集时间/入库时间分离；
- 保持旧 CLI 烟测可用。

### 交付物

- `src/store/db.js`：连接、WAL、事务、迁移入口；
- `src/store/schema.sql` 或迁移脚本；
- `src/store/raw_queue.js`：登记、扫描、认领、完成、失败、归档；
- `src/store/job_store.js` 适配：写主库 `jobs`；
- `src/ingest/job_ingest.js`：从队列取文件，幂等 upsert；
- `src/core/time_utils.js`：采集时间→日期；
- 迁移脚本：现有 `job_store.json`/outputs；
- 测试：队列、幂等、跨天、采集时间。

### 数据表（最小）

```text
raw_files
jobs
job_numbering
job_duplicates
ingest_runs
```

### 验收

- [ ] 11 号采集、12 号入库，岗位显示 11 号；
- [ ] 两次采集同一岗位不重复建、不重复占号；
- [ ] 入库失败可重试；
- [ ] 处理所有 pending，不只当天；
- [ ] 旧离线烟测仍通过。

### 风险

- 现有 JSON 存储与 SQLite 并存导致双写不一致 → 先做适配层，S1 只让新链路写 SQLite，旧 CLI 只读/兼容；
- Node 22.4 的 SQLite 驱动选择 → 优先 `better-sqlite3` + Electron rebuild，或 `node:sqlite`（需验证 Electron 版本）。

## 9. 偏离度检查

每阶段结束做一次：

1. 需求 ID → 实现/测试映射；
2. 未实现项标注原因；
3. 与 PRD 不一致处列出；
4. 是否影响下一阶段；
5. 是否需要用户决策。

最终整体检查：

- 全链路（登录→采集→raw→入库→评分→日报→导出）；
- 异常（登录失效/风控/卡住/崩溃/断网）；
- 数据一致性（编号/重复/关闭/重开/时间）；
- 性能（3 角色×2 平台×6 子任务）；
- 安全（Key/简历/日志）。
